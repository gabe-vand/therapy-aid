Architecture

How therapy-aid turns a weekly therapy session into something Gabe still has next week: the intake pipelines, the data model, and how the AI is grounded. Sections 6–10 (model routing and cost, auth, where data lives on the Pi, seeding and backups, failure behaviour) are on the operations page. Read both before changing a pipeline, a prompt, or the deploy.

Shape: one SPA · one API process · one SQLite file  ·  AI: Claude (per-task models) + Deepgram  ·  Reach: tailnet only  ·  Last updated: 2026-11-03
Occam's razor is the design rule. No queue, no vector database, no streaming, no background worker process. Each of those would be a second moving part for a corpus of a few dozen documents and a single user. If something here looks under-built, it is because the simpler thing is correct (§4 and §5 say why).

The big picture

The problem: by next week the session is forgotten, trends are invisible, and advice evaporates. The app keeps three things alive between sessions: what was said (sessions), what it adds up to (problems, and the focus banner derived from them), and what Gabe wrote himself (journal). Chat and the “I have an idea…” button are two ways to ask questions of all of it.

phone / laptop on the tailnet
   |  https://therapy-aid.elephant-trench.ts.net
   v
ts   (Tailscale sidecar: TLS, adds Tailscale-User-Login)
   v
web  (nginx: SPA, and /api/* with the prefix stripped; 50 MB bodies, 600 s timeouts)
   v
api  (Bun + Hono, port 3010)
   routes  ->  services  ->  repositories  ->  SQLite  (/data/therapy-aid.sqlite)
                 |
                 +-> Anthropic API   (summaries, problem mapping, focus, insight, chat)
                 +-> Deepgram API    (diarized transcription of recordings)

The layering rules (routes never see the database, queries live only in repositories, components never fetch) are in the backend and frontend conventions. This page is about what the pieces do together.

2

Session pipelines — two doors, one record

A session arrives either as a recording (made in the browser during the live session) or as notes (pasted afterwards, also how history is seeded). Both end up as the same row, with the same summary, and the same effect on problems.

RECORDING                                     NOTES
 browser MediaRecorder, a chunk every 30 s     POST /sessions/notes
 POST /sessions/:id/chunks?seq=N (in order)         |
 POST /sessions/:id/finalize {chunk_count}          |
   (no count = take the chunks on disk: the
    "Finish this recording" salvage)                 |
        |                                           |
   status: uploaded  <-------------------------------+
        |
   transcribing   Deepgram nova-3, diarized -> "[mm:ss] Speaker N: ..."   (recordings only)
        |
   summarizing    call 1 (summarize):     transcript/notes -> title, overview, key points, therapist advice
        |         call 2 (map_problems):  that SUMMARY + the problem list -> progress notes, new problems
        |         apply: problem_updates rows, last_discussed_at, new problems, resolved suggestions
        |         reindex search
        v
   ready          (or failed, with a readable error; Retry resumes at the failing step)
        |
   then, best-effort: regenerate focus (whole-picture call). It runs AFTER ready and a failure is
   only logged: the session stays ready, and Home offers "Generate my focus" / Refresh.
  • Chunked upload, in order. Chunks are appended strictly by sequence number; an out-of-order chunk is a 409 carrying the expected number, and finalize verifies the count. A phone that loses signal mid-session loses nothing it already sent, and the browser keeps unacked chunks in memory and retries them.
  • Two narrow calls instead of one big one. The second call sees a ~1k-token summary rather than a 10k-token transcript, and each call has one job. That is what makes cheaper models viable (§6).
  • One session at a time. Processing runs through an in-memory promise chain, so a session's problem mapping always sees the previous session's problems. This is what makes seeding six notes in order correct, and it is why there is no queue: the chain is the queue.
  • Never throws, always resumable. The pipeline catches everything, stores a human-readable error and sets failed. A transcript is kept, so Retry after a missing API key redoes only the failed step. At boot, anything left in uploaded, transcribing or summarizing by a restart is re-queued. A recording that no audio has reached for 30 minutes (a dead phone, a closed tab) is marked failed with its audio kept for Retry; that sweep runs at boot and every 5 minutes (services/sessions/recovery.ts), because the Pi runs for weeks between restarts. Sooner than that, the session page offers Finish this recording. A failure after the summary was saved keeps the summary visible under the error. Edits to the title or date made while a call is in flight win: the pipeline re-reads the row after each await.
  • The audio stays on disk whatever happens to the AI steps, so a missing Deepgram key costs a Retry, not a lost session.
3

Data model

Plain SQLite tables, one DDL file each in backend/db-schemas/, mirrored by Drizzle entities. Timestamps are ISO-8601 UTC text; occurred_at is when the thing happened (editable), created_at is when the row was made.

TableHolds
sessionsOne per therapy session: source (recording | notes), status (recording, uploaded, transcribing, summarizing, ready, failed), notes, transcript, summary_json, error, audio path and mime, duration.
problemsDurable threads (“racing mind”, “Nicole”): status active | resolved | discarded, last_discussed_at, last_reviewed_at, origin_session_id.
problem_updatesThe timeline of each problem: one progress note per session that touched it (source ai) or by hand (manual). Deleting a session keeps its notes and nulls the link.
focus_snapshotsEvery regenerated “what to focus on now” (headline + 1–3 items). The newest is the banner; older ones are history.
journal_entries, journal_insightsJournal text, and the insights generated on request for an entry.
chat_threads, chat_messagesConversations with the grounded chatbot.
app_settingsKey/value; today just profile, the “About me” text every prompt opens with.
search_indexAn FTS5 virtual table (porter unicode61), one row per session or journal entry, rewritten on every write and rebuilt at boot if empty.

Problems are the memory. Sessions are events; a problem is the thing that persists across them. Each session is mapped onto existing problems wherever the topic matches, even loosely, and only opens a new one for a durable theme. A problem not discussed or reviewed for 30 days is flagged stale and the Home page asks whether it is still relevant (Keep bumps last_reviewed_at; Discard hides it).

4

Grounding — the context pack, then retrieval

Chat, focus and insights all answer from the same grounding text, built by services/context/context-pack.ts:

  1. About Gabe — the profile.
  2. Current focus — the latest snapshot.
  3. Problems — active ones with description, last discussed and the two newest notes; resolved ones by title.
  4. Therapy sessions (newest first) — each ready session's overview, key points, and what David suggested.
  5. Recent journal entries — the last eight, each capped at 700 words.
  • Budget about 30k tokens. When over, the oldest sessions degrade to one line (date, title, key points), then the oldest one-liners drop with a pointer to search. Recent sessions keep their full depth; old ones stay findable.
  • Deterministic. No clock, no randomness: the same rows produce a byte-identical pack. That is not tidiness, it is what lets prompt caching work (§6). Every item carries an id handle ([session #4], [problem #3], [entry #12]) the model can cite and pass back to a tool.
  • Therapy outranks journal. The pack lists sessions first and the prompts say so: when David's advice and Gabe's own journal self-advice conflict, David's wins.

Retrieval on top. For each chat message the server runs a deterministic FTS5 search on the message itself (stopwords dropped, terms quoted so a stray " cannot break the query, 4+ character terms prefix-matched) and puts the top hits in the user turn as “Possibly relevant excerpts”. The model also has three tools — search_notes, read_session, read_journal_entry — for following up. Cheaper models are far better when handed evidence than when asked to go and find it.

5

Why not embeddings

  • The corpus fits. Years of weekly sessions, summarized, are tens of thousands of tokens. The recent, high-value part sits in the prompt whole; the rest is one line each. Nothing needs to be “retrieved” to be seen.
  • Keyword search is the right tool for this text. Gabe's questions name things (“Nicole”, “panic”, “racing mind”). BM25 over stemmed words with prefix matching finds them exactly, and shows why it matched (the snippet), which a similarity score cannot.
  • No second system. Embeddings mean a model dependency, a vector store, a re-embedding job on every edit, and a Pi that has to run or call all of it. FTS5 ships inside SQLite and is rewritten in the same transaction as the document.
  • The model is the semantic layer. It reads the pack, so it already connects “can't switch off at night” to a session about a racing mind. It only needs help finding a specific passage, and search plus tools does that.
  • Revisit when the pack can no longer hold the recent sessions at useful depth, or a question keeps missing because the words differ from the notes. Neither is true at dozens of documents.
