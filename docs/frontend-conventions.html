Frontend Coding Conventions

The source of truth for frontend code style across therapy-aid. Read before any work in frontend/. Adapted from rx-unified-portal's conventions.

Stack: Vite + React 18 + TypeScript + Tailwind v4  ·  Runtime: Bun  ·  Routing: react-router v6  ·  Design: token-driven (src/styles/tokens.css)  ·  Tests: required (Vitest + React Testing Library on happy-dom).
Components never touch the network. Every API call lives in a services/hooks/use-*.ts hook that owns its loading and error state. See §5.

1

Tokens, not colours

Every colour is a CSS custom property from src/styles/tokens.css (var(--ink), var(--surface), var(--accent), …), defined once for light and once for dark. Never a hex literal in a component. A new colour is a new token. Tailwind is for layout utility; the visual identity comes from the tokens. The token set, theme, page widths, primitives, mobile and editor rules live in Frontend Styling & UI — read it before touching styles or layout.

2

Declarative

State → derived state → render. No imperative DOM mutation.

3

snake_case on the wire and inside functions

  • JSON keys and store fields: snake_case.
  • Internal function variables and hook return fields: snake_case (record_visit, set_status).
  • React-owned identifiers (onClick, className, useFoo) and component names keep framework casing.

A type the API also declares belongs in @therapy-aid/shared, not in a second copy under src/services/types/. What stays in the SPA is what the SPA alone knows: view-models, editor state, and request payloads whose server-side twin is deliberately looser.

Formatting is Prettier's job: the one root .prettierrc. Run bun run format.

4

File size — hard cap

Every file stays below 200 lines — components, hooks, pages, tests, everything. Split pages into feature components early: a screen is usually one page file plus 3–6 section components under components/<feature>/. Enforced by backend/tests/architecture/file-size.test.ts.

5

Hooks are the only way to do API calls and shared logic

  • Components never call fetch or services/api.ts directly. Every API call lives in a custom hook (services/hooks/use-<domain>.ts) that owns loading and error state.
  • services/api.ts resolves to the { data, status_code, message } envelope and never throws — a network failure becomes an envelope with a human message.
  • Mutation hooks expose an explicit trigger; they do not auto-fire.
  • An auto-loading hook must drop a superseded response. Pass a cancel flag into the loader and check it after every await, immediately before the set_* calls: useEffect(() => { const signal = {cancelled:false}; load(signal); return () => { signal.cancelled = true; }; }, [load]). use-hello.ts is the reference.
  • A destructive action gates on loading, not just on a count — before data arrives the count is zero.
6

State

  • useState for local UI. When state genuinely needs sharing across screens, add Zustand (persisted where it should survive a reload) under services/store/ — don't reach for it before then.
  • localStorage for identity/selection, sessionStorage for drafts, none for ephemeral UI.
7

Error handling — graceful, always

  • Every async call has a success path and a failure path — no infinite loading.
  • No silent catch {}. Show the envelope's message, never a raw exception.
8

Environment variables

Read import.meta.env.* only through services/env.ts. VITE_API_BASE_URL stays unset — the SPA calls the relative /api, which nginx (Pi) and the Vite dev proxy forward. .env.example is committed; never put secrets in VITE_ vars — they ship in the bundle.

9

Idempotent

Strict-mode double-mount, repeated mutations, and store rehydration must be safe. Never push to arrays without dedup; derive counters, don't increment them.

10

Documentation lives in docs/, nowhere else

No .md under src/. Prose about a feature goes in docs/ (HTML); the why of a given file goes in its header comment. Update the repo-root features.html with every update.

11

Comments — why, not what

Above every component and hook: what and why. Inside: a comment per logical group, only where the code doesn't already say it.

12

Tests — required

  • Vitest + @testing-library/react + @testing-library/jest-dom on happy-dom. Matchers wired once in tests/setup.ts.
  • Test files live in tests/ mirroring src/, glob tests/**/*.test.{ts,tsx}. Shared fixtures go in tests/helpers/hlp-*.ts.
  • Stub fetch per test with vi.stubGlobal (see hlp-fetch.ts); setup.ts unstubs after each test so nothing leaks.
  • Every new hook and component gets tests; touching untested code adds tests for the part touched.
13

Always check the latest docs before coding

Use Context7 if available; otherwise the official docs. Don't write API calls from memory — React, Tailwind v4, Vite and Bun change.

14

When you touch old code

You also:

  • Convert stray camelCase JSON keys, store fields, and variables to snake_case (§3).
  • Add types where missing, and unit tests for the part you're changing (§12).
  • Split the file if it is at or over the 200-line cap (§4).
  • Move any direct API calls in components into hooks (§5).
  • Replace silent or ad-hoc error handling with the patterns in §7.
  • Update the comments (§11), the relevant docs/ page (§10) — and features.html.
