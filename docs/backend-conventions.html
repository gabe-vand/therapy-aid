Backend Coding Conventions

The source of truth for backend code style across therapy-aid. Read before any work in backend/. Adapted from rx-unified-portal's conventions — same layering and discipline, with SQLite in place of a shared Postgres.

Stack: Bun + Hono + TypeScript  ·  Database: SQLite (bun:sqlite) + Drizzle  ·  Hosting: Docker Compose on the Pi, tailnet only  ·  Tests: required (bun test ./tests).
The layering rule governs everything here. Routes → services → repositories → entities, and a query lives only in a repository. tests/architecture/layering.test.ts fails the suite on any shortcut. See §13.

1

Declarative

Express schemas, types, route definitions. Pure functions where possible; side effects at the edges.

2

snake_case on the wire and inside functions

  • JSON API keys: snake_case (the envelope is { data, status_code, message }).
  • SQLite column names: snake_case.
  • Internal function variables: snake_case. Function names camelCase (getHelloStatus, dbMigrate); routers router_<module>.
  • Types/interfaces PascalCase; env vars and constants UPPER_CASE.
  • File/folder names: kebab-case. Inside the layer dirs files carry no role prefix — the directory conveys the role (routes/hello/hello.ts). Role prefixes remain only for shared infra: svc- (services/common), md- (middleware), hlp- (test helpers).

A response shape the SPA also declares belongs in @therapy-aid/shared (packages/shared/src/types/), imported by the service that produces it — two identical interfaces on either side of the wire are two things that can drift. Internal shapes (row types, the pre-validation request body) stay in the module.

Formatting is Prettier's job, not yours: the one root .prettierrc — 4-space indent, 250 print width, single quotes, trailing commas, semicolons. Run bun run format.

3

SQLite — one file, one process

  • The database is a single SQLite file opened once in svc-db.ts with WAL, a 5 s busy_timeout and foreign keys on. bun:sqlite is built into Bun — no native module to compile on the Pi.
  • Queries use the Drizzle builder (db) by default. A raw statement (sqlite.query(…)) is fine where Drizzle has no equivalent — always with bound parameters, never string-concatenated SQL. Either way it lives in a repository (§13).
  • Exactly one process writes the file: the api container. Never point a second process (a local dev server, a script) at the Pi's database file.
  • On the Pi the file is /data/therapy-aid.sqlite in the db-data volume. It survives every redeploy; docker compose down -v deletes it.
4

Idempotent DDL and inserts

  • All DDL lives in backend/db-schemas/NNN.<table>.sql, applied by dbMigrate() on every boot, in filename order, each file in its own transaction — so every statement is rerunnable (create table if not exists, create index if not exists).
  • One file per table. A new number is for a new table. Every later change to that table is appended under its own DDL, dated in a comment. There is no applied-ledger, so a new number buys nothing and scatters one table's shape across the directory.
  • SQLite has no add column if not exists, so a plain alter table … add column fails on the second boot. When the first such change comes, give svc-migrate.ts a guarded step that checks pragma_table_info before altering, and test that a second boot is a no-op.
  • Every seed/insert uses on conflict do nothing / on conflict do update.
  • tests/services/common/svc-migrate.test.ts enforces the naming and the if not exists rule, and that a second run is a no-op.
5

File size — hard cap

Every file stays below 200 lines. Split proactively: routers per feature, helpers per concern, schema files per domain. tests/architecture/file-size.test.ts enforces it across the whole workspace, frontend included.

6

Error handling — graceful, always

  • Every response — success or failure — goes through rsp(c, data, stc, message); never raw c.json. rsp sets the real HTTP status too.
  • No silent catch {}: log with a [module] prefix, then answer. Client-facing errors never leak internals, stack traces, paths or SQL. app.onError in app.ts is the last-resort net.
  • /health is reachable by anyone on the tailnet: booleans and the revision only.
7

Environment variables — structured and commented

  • Read env ONLY through app_env in svc-env.ts — never process.env.X elsewhere. Boot validates via getEnvStatus() and exits loudly on a missing mandatory var.
  • Every var has a working local default where one is safe, so bun run dev needs no env file.
  • backend/.env.example is committed with placeholders, grouped and commented. Real values never enter the repo; on the Pi, secrets go in ~/therapy-aid.env (outside the deploy dir, which is replaced every deploy).
  • Any new var lands in EnvKey + app_env (+ MANDATORY) + .env.example in one commit.
8

Documentation lives in docs/, nowhere else

There are no .md files under src/. Prose about a feature goes in docs/ (HTML), and the why of a given file goes in that file's header comment (§9). Update the repo-root features.html with every update — it is the implemented / not-implemented ledger.

9

Comments — why, not what

A header comment on every file saying why it exists. Above every exported function: what it does and why. Inside: a comment per logical group, only where the code doesn't already say it.

10

Tests — required

  • Every repository function, service, handler and helper gets tests under tests/, mirroring src/.
  • tests/helpers/hlp-test-env.ts is preloaded (bunfig.toml) and points DB_PATH at :memory: before any module opens the database. Tests run against a real, empty SQLite — prefer that over mocking repositories; it is fast and it tests the SQL.
  • Routes are tested through app.request() on the real app — no port, no server.
  • mock.module is global and first-load-wins in Bun: if you must stub, always spread the real module first ({...(await import(M)), stubbed}), and prefer spyOn over a namespace import for anything that has its own test.
  • Idempotency is tested explicitly.
11

Always check the latest docs before coding

Use Context7 if available; otherwise the official docs. Don't write API calls from memory — Bun, Hono and Drizzle all change.

12

When you touch old code

You also:

  • Convert stray camelCase JSON keys, columns, and variables to snake_case (§2).
  • Add types where missing, and unit tests for the part you're changing (§10).
  • Make any non-idempotent migration/seed idempotent (§4).
  • Split any file at or over the 200-line cap (§5).
  • Replace silent or ad-hoc error handling with the patterns in §6.
  • Update the comments (§9), the relevant docs/ page (§8) — and features.html.
13

Layered architecture — routes → services → repositories → entities (critical)

Central layer directories, functional style throughout (no classes, no DI):

  1. src/routes/<module>/<router>.ts — thin Hono routers: parse body → guard → call a service → rsp(). Never import svc-db, drizzle-orm, or a repository. One folder per module, even for a single file — no naked files directly under src/routes/.
  2. src/services/<module>/<topic>.ts — business logic. Calls repositories; never imports drizzle-orm, svc-db, or Hono. Only services/common (and later services/middleware) is exempt — and even there, queries live in repositories: svc-db/svc-migrate are the DB plumbing itself.
  3. src/repositories/<module>.ts — the only place a query may live. One narrow function per query (params in, rows out, no business logic).
  4. src/db/schema/*.ts — Drizzle entities mirroring the DDL; imports nothing but drizzle-orm.

src/app.ts holds the mount table; src/index.ts only boots. Hono-Context helpers belong in the module's routes/<module>/common.ts, never in services. tests/architecture/layering.test.ts checks each layer's import bans file by file.
