Model routing and cost

No call site names a model. Each AI call names a task and svc-models.ts resolves its model and reasoning effort, so cost is tuned in one table (and per task through CLAUDE_MODEL_<TASK> / CLAUDE_EFFORT_<TASK>, or everything at once with CLAUDE_MODEL).

TaskDoesWhy this tier
summarizetranscript or notes to title, overview, key points, adviceFaithfulness to the source matters most; one narrow job.
map_problemssummary + problem list to progress notes and new problemsOpus: the eval showed problem mapping is the long-lived structure and Sonnet opens practices (meditation, routines) as problems. The call is small (a ~1k-token summary, not the transcript), so Opus costs about $0.03 a session.
focuswhole picture to headline + 1–3 actionsThe one judgment call over everything; runs once per session.
insighta whole journal entry x the context pack to a reflectionOnly on request (“Reflect on this entry”).
classifyone finished journal paragraph to the problem it is about (id + confidence), or noneHaiku, low effort: a label against a short cached list, run on every paragraph Gabe finishes (about $0.0001 a call), so it has to cost nothing. Feeds the journal↔problem links.
margin_notea confident match + narrow evidence to a 25–60 word margin noteSonnet over the problem's notes and the three sessions that match the paragraph (not the whole pack): about half a cent a note, and the writer only runs when the classifier is confident and the cadence allows.
chatgrounded answers with toolsEvidence is pre-retrieved, so a mid-tier model suffices.
titlemechanical namingCheapest tier.

The shipped defaults are in TASK_MODELS; the model eval is how they are changed, by running the real prompts on real notes across tiers and comparing outputs, not by guessing. bun run eval (scripts/eval-models.ts, key from backend/.env) imports the prompt builders and svc-claude directly, with no server and no database file: the rows a run would write live in memory (scripts/lib/eval-world.ts) and are rendered by the same pack-section functions. For each --models entry it summarizes the six seed notes in order, maps each onto the problems the earlier ones produced, then writes one focus, one insight on the 2026-10-13 journal entry and three chat answers, into eval-out/<model>/, with eval-out/costs.md from the usage log. --judge has Opus grade every cheaper model against Opus (faithfulness, problem mapping, usefulness, tone; 1–5 with a reason) into eval-out/judge.md. The judge is an aid; read the raw outputs before moving a task to a cheaper tier.

  • Prompt caching. For chat, focus and insight the system prompt is the persona plus the context pack, both marked cacheable and byte-stable; today's date, the draft and the question go in the user message. Repeated chat turns and insights read the large block at a fraction of the input price. The two session-processing calls (summarize, map_problems) cache only their static instructions: their per-session context (profile, problems, recent sessions) changes every session, so it rides in the user message and cached= stays small for them during seeding. That is expected, not a caching bug. The log line shows cached= so it can be verified.
  • See the bill. Every call logs one line (task, model, input / cached / output tokens, estimated dollars) and adds to in-memory per-task totals, served at GET /ai/usage and shown under Settings. Totals reset when the API restarts.
  • Structured output uses the SDK's zod parse with schemas that carry no hard length limits; limits are written into the prompt and clamped in code, because a violated schema discards the whole (paid-for) reply.
  • Automatic only where it is nearly free. Reflections and regenerate-focus happen on a click. Margin notes are the one companion that runs on its own while Gabe writes, and it is built to be cheap: a Haiku classification per finished paragraph, and a Sonnet note only on a confident match, at most one a minute, five an entry and forty a day (services/journal/margin/). The switch in Settings turns it off per device. The other automatic AI work is processing a session the user just added.

Auth

There are no passwords or sessions. tailscale serve authenticates each request against the tailnet and adds a Tailscale-User-Login header; md-auth.ts allows a request only when that header equals ALLOWED_TAILSCALE_LOGIN (case-insensitive). Everything except /health is behind it, 404s included. GET /me returns the login.

  • Fails closed. With the variable empty, development allows everything as dev@local; any other environment rejects every request with 401 and logs it once at boot. Forgetting the setting locks the app; it never opens it.
  • Funnel is off, so no public request can reach the sidecar; the header cannot be forged from outside the tailnet. The one host port is 127.0.0.1:8080 on the Pi, where a local shell could send its own header, which is an accepted risk on a single-user box.
  • Another tailnet member (shared device, shared node) is rejected too: being on the tailnet is not enough, the login has to match.
  • CSRF. The login header rides on every request from the owner's browser, whichever page made it, and a cross-site text/plain POST needs no preflight. md-same-origin.ts, ahead of md-auth, refuses (403) any non-GET whose Sec-Fetch-Site is not same-origin/none, or, from a browser without that header, whose Origin is not this host. Clients that send neither (the import CLI, curl) are not browsers and pass.
  • Dev binds to 127.0.0.1. Development auth lets everything in as dev@local, so bun run dev:api listens on loopback only; the container (APP_ENV=production) listens on all interfaces for nginx.
  • CSP. nginx serves the SPA with a same-origin-only Content-Security-Policy, and the markdown renderer drops images, so a prompt-injected answer cannot make the browser send text to another server.

Where data lives on the Pi

WhatWhereSurvives
SQLite databasevolume db-data, /data/therapy-aid.sqliteredeploys, compose down; not down -v
Session audiosame volume, /data/recordings/<session id>/ (chunks, then one audio.<ext>)same as above; deleting a session deletes its folder
Daily snapshotshost folder ~/therapy-aid-backups/ (mounted at /backups)everything, including down -v; database only, no audio
Tailscale identityvolume ts-stateredeploys
API keys, login, tuning~/therapy-aid.env (mode 600), outside the deploy direverything; read by compose at deploy time
The code~/therapy-aid, replaced wholesale on every deploynothing: keep no state here
Never run docker compose down -v on the Pi. It deletes the database and the recordings together. Snapshots survive it, but the audio does not.

Data sent off the Pi: session text and journal text go to Anthropic with each AI call; recordings go to Deepgram. Both are API calls on the owner's keys. Nothing else leaves.

Seeding and backups

  • History is imported over HTTP, from a dev machine. scripts/import-seed.ts reads the local, gitignored seed-data/ and calls the same API the app uses: profile, journal, then therapy notes oldest first, waiting for each to be ready before sending the next (§2). Re-running skips what exists and retries what failed. Runbook: the /ship skill, “Seeding history”.
  • Personal data never enters the repo. It is public. seed-data/ and eval-out/ are gitignored, so they are also absent from git archive, which is all that ships.
  • Backups: one VACUUM INTO snapshot per UTC day, integrity-checked, 30 kept, reported by /health as backup_ok. They share the Pi's SD card; copying them off the Pi and backing up the audio are open items on features.html.

Failure behaviour

WhenWhat happens
No ANTHROPIC_API_KEYThe app runs. Reading and writing journal, problems and settings work; every AI feature fails with a message that says what to set. A session fails at summarizing and can be retried.
No DEEPGRAM_API_KEYNotes work. A recording fails at transcribing with a clear message; the audio is kept for Retry.
Model refuses, or the reply is cut off or fails its schemaA readable error on the session or chat turn, never a stack trace. Rate limits and 5xx are retried by the SDK first.
API restarts mid-pipelineBoot re-queues interrupted sessions.
Phone dies or tab closes mid-recordingThe uploaded chunks are safe. The session page offers Finish this recording; otherwise a sweep (boot + every 5 min) fails it after 30 minutes without audio, keeping the audio for Retry.
Phone loses signal while recordingUnacked chunks stay in the browser and retry; the server enforces order, so nothing is silently dropped or duplicated.
Search index lost or emptyRebuilt from the tables at boot.
